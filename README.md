# graphbench

Benchmark suite comparing **CognoDB Cloud** against four other managed graph
database platforms on identical data and identical logical queries, for the
Wexa AI take-home assignment (`docs/assignment.pdf`).

## Status

**No platform has been measured yet.** Every table in the [Results](#results)
section below is generated directly from `results/raw/*.jsonl` by
`analysis/render_readme.py` - right now that directory is empty, so the
tables say so honestly instead of showing a number. See
[Known limitations](#known-limitations) and `results/failures.md` for why,
and [Reproducing this benchmark](#reproducing-this-benchmark) for how to
actually run it once Stage 0 (provisioning five free-tier accounts) is
done.

Every adapter, workload, and the harness itself are written and unit-tested
against a `FakeAdapter` (confined to `tests/`, unreachable from `cli.py`),
but none have been executed against a live database - see the constraint
below.

## Objective

Design and run a benchmark suite that compares CognoDB.com with four other
managed graph database cloud platforms on the same dataset and the same
workloads, under the same resource limits, measuring the metrics in section
5.2 of the assignment: ingest throughput, 1/2/3-hop traversal latency, point
and filtered lookup latency, an aggregation query, mixed read/write
throughput under a concurrency sweep, and footprint where observable.

## Platforms

| Platform | Query language | Adapter | Advertised specs | Card required |
|---|---|---|---|---|
| CognoDB Cloud | Cypher (Bolt) | `adapters/bolt.py` | burstable 0.5 vCPU / 256 MB RAM / 1 GB disk (`docs/assignment.pdf` §3) | No |
| Neo4j AuraDB Free | Cypher (Bolt) | `adapters/bolt.py` | *unknown - see below* | *unknown* |
| Memgraph Cloud | Cypher (Bolt) | `adapters/bolt.py` | *unknown - see below* | *unknown* |
| FalkorDB Cloud | Cypher subset (RESP) | `adapters/falkordb.py` | *unknown - see below* | *unknown* |
| ArangoDB Oasis | AQL (deliberately non-Cypher) | `adapters/arangodb.py` | *unknown - see below* | *unknown* |

CognoDB, Neo4j AuraDB and Memgraph Cloud all speak the official Bolt
protocol, so they share one adapter (`adapters/bolt.py`) - adding any of the
three touched only a `config/platforms.yaml` block, not a new file, which is
exactly the "adding a platform" contract `CLAUDE.md` asks for.

The four *unknown* spec rows are not a placeholder for a number I didn't
feel like looking up - the environment this repo was built in cannot reach
any of these providers' marketing or docs pages (see
[Known limitations](#known-limitations)). Fill them in from each console
during Stage 0 and replace the `null` fields in `config/platforms.yaml`
under `advertised_specs`; `render_readme.py` does not currently source this
table from that file, so update both.

**Fairness note (assignment §3):** the assignment requires sizing the
dataset to fit the smallest tier and running every platform under
equivalent resources. CognoDB's free tier (256 MB RAM) is the binding
constraint. Track A here means "each platform's own free/entry tier as
shipped" - product parity, not hardware parity, since a managed free tier's
actual CPU/RAM allocation is rarely fully disclosed or independently
verifiable. Track B (self-hosted, `docker/compose.capped.yml`, `--cpus=0.5
--memory=256m` plus a 256/512/1024/2048 MB sweep) is the harder, apples-to-
apples comparison for the two self-hostable engines (Memgraph, FalkorDB),
and has not been run - see Known limitations.

## Dataset

**Source:** [MUSAE GitHub developer-network dataset](https://github.com/benedekrozemberczki/MUSAE)
(Rozemberczki & Sarkar, *Multi-scale Attributed Node Embedding*, Journal of
Complex Networks, 2021), fetched from
`https://raw.githubusercontent.com/benedekrozemberczki/MUSAE/master/input/edges/git_edges.csv`
and `.../input/target/git_target.csv`.

- **37,700 nodes** (GitHub developers), **289,003 relationships** (mutual
  follower edges) - verified by direct download and line count, not asserted
  from the paper.
- One binary node property, `ml_target` (web vs. ml developer classification
  from the paper), used for the filtered-lookup and aggregation workloads.
- Already inside the assignment's required 100k-500k relationship range, so
  `dataset/sample.py`'s seeded BFS/snowball sampler is present and
  unit-tested but was not triggered for this run (`sample_method:
  "identity-already-in-range"` in `data/manifest.json`) - no edges were
  discarded for no reason.
- Full provenance (URL, retrieval timestamp, SHA256 of both CSVs) is in
  `data/manifest.json`, regenerated by `make dataset`.

**Why not the assignment's suggested SNAP/social-network sources:** the
environment this repo was built in can only reach GitHub and package
registries (see Known limitations) - `snap.stanford.edu` and every other
dataset host tried returned a hard network denial. The MUSAE dataset is a
real, peer-reviewed, appropriately-sized substitute, not an invented one;
re-pointing `dataset/fetch.py` at SNAP (e.g. `soc-Pokec`) once real network
access is available is a same-shape change, not a redesign.

**Why not LDBC SNB directly:** the workload shapes below (single-hop
neighbor lookup, N-hop traversal, point/filtered lookup, group-by
aggregation, mixed read/write) are modelled on LDBC Social Network
Benchmark's *interactive short-read* query patterns, simplified to this
dataset's single node label and single relationship type. Full LDBC SNB has
a multi-entity schema (persons, posts, comments, forums, tags, places...)
and its generator's smallest practical scale factor still produces a
multi-GB working set once loaded with indexes - well past the CognoDB free
tier's 256 MB RAM / 1 GB disk ceiling this benchmark is deliberately sized
to fit under.

## Methodology

- **Same logical queries everywhere.** Each adapter's `QUERIES` dict is the
  only place query-language text differs; `graphbench/workloads/` code
  never touches query text, only logical names (`hop_1`, `point_lookup`,
  ...) and parameter values.
- **Result-equality gate before any latency is trusted.** `core/validate.py`
  runs every logical query against 20 fixed sample nodes on every platform
  and compares a sha256 fingerprint of the canonicalised result set
  (`make validate`). A mismatch aborts with a diff rather than being
  averaged away.
- **RTT floor.** `rtt_probe_ms()` (100 samples of a trivial query) is
  measured on every platform so cross-region network latency can be told
  apart from database latency.
- **Degree-stratified sampling.** Start nodes are bucketed into low
  (p10-p30), mid (p45-p55) and high (p90-p99) degree bands
  (`core/sampler.py`, fixed seed, `data/start_nodes.json` committed); the
  same node IDs are replayed on every platform. Uniform random sampling
  would let p95 measure which hubs the sampler happened to hit rather than
  database performance.
- **Warm-up, separated.** Every read workload runs `warmup_iterations`
  (`phase="warmup"`, discarded) before `measured_iterations`
  (`phase="measure"`) - see `config/workloads.yaml`.
- **Open loop for the mixed workload.** `core/runner.run_open_loop`
  precomputes intended start times per client and records
  `queue_delay_ms = actual_start - intended_start`; a run whose queue delay
  trends upward is flagged invalid rather than published (`cli.py`'s
  `sweep` command checks this against
  `mixed_workload.queue_delay_trend_max_slope_ms_per_min`).
- **Burst credits.** The mixed workload runs for
  `mixed_workload.duration_seconds` (currently 1200s = 20 minutes) at each
  concurrency level, so a free-tier CPU-credit exhaustion cliff has room to
  show up in the time series rather than being cut off.
- **Raw records only.** Every request appends one `Record` (one JSONL line)
  to `results/raw/<run_id>.jsonl`; all percentiles and rates in this README
  are computed from those raw rows by `analysis/`, never written to disk as
  a precomputed summary.

## Reproducing this benchmark

1. **Stage 0 (human, not scriptable):** sign up for CognoDB, Neo4j AuraDB
   Free, Memgraph Cloud, FalkorDB Cloud and ArangoDB Oasis; provision one
   free instance each. Copy `.env.example` to `.env` and fill in every
   variable named in `config/platforms.yaml`.
2. `pip install -r requirements.txt`
3. `bash scripts/install-hooks.sh` (installs the gitleaks pre-commit hook)
4. `make dataset` - fetches and writes `data/nodes.csv`, `data/edges.csv`,
   `data/manifest.json`
5. `make sample` - writes `data/start_nodes.json` (degree-stratified,
   commit this file so every platform replays identical node IDs)
6. For each platform in `config/platforms.yaml`: `make load PLATFORM=<name>`
   then `make bench PLATFORM=<name>`
7. `make validate` - the cross-platform result-equality gate; fix any
   reported mismatch before trusting the numbers from step 6
8. `make sweep PLATFORM=<name>` - mixed workload, 1/10/40 concurrency
9. `make report` - regenerates this README's Results section from
   `results/raw/*.jsonl`

`make check` runs `ruff check .`, `mypy --strict`, and `pytest -q`.

## Anomalies observed

None yet - there is no data to observe an anomaly in. This section is meant
to be a bullet list of things in the raw numbers that looked surprising
enough to need an explanation (a platform's p95 spiking at one concurrency
level, a hop_3 query timing out on one platform but not others, a burst
credit cliff partway through the 20-minute mixed run); root-cause analysis
of *why* belongs in the analysis prose, written by a human after looking at
real numbers, not generated here.

## Threats to validity

| Threat | Mitigation | Residual risk |
|---|---|---|
| Query-language semantic drift (Cypher variable-length match vs. AQL `uniqueVertices: 'global'` traversal for hop_2/hop_3) could make one platform's traversal return a different node set than another's for the same logical query, without either being "wrong" | `core/validate.py`'s fingerprint gate runs before any latency is trusted, on the exact queries being benchmarked | A mismatch caught by the gate stops the benchmark rather than silently comparing non-equivalent results - but if it fires, the fairest fix (loosening one platform's query) may itself change what's being measured, and has to be judged case-by-case |
| Managed free-tier "specs" are marketing claims (burstable, not guaranteed) rather than measured hardware | `rtt_probe_ms()` and the mixed-workload burst-credit time series measure *behavior* under load rather than trusting the advertised number | A platform can still look faster purely because its burst credit pool is larger/renews faster at the moment of the test, not because the database engine is faster |
| Cross-region network latency getting counted as database latency | RTT floor (100-sample trivial-query probe) reported alongside raw latency for every platform | If instance region isn't recorded per platform (see Known limitations), the RTT floor can't be attributed to a specific network path with confidence |
| Free-tier throttling or a transient outage during a run gets misread as a real performance difference | Every failure becomes a `Record` with `ok=False`, not a retry or a silently dropped sample; `make validate` and the queue-delay-trend check catch a generator or platform falling behind | A platform failing mid-run for reasons unrelated to performance (e.g. a maintenance window) still shows up as bad numbers unless someone reads `results/raw/` and notices the `ok=False` rows |
| Dataset substitution (MUSAE GitHub network instead of an original SNAP-hosted graph) changes degree distribution, clustering, and therefore traversal fan-out vs. what the assignment's suggested sources would produce | Documented prominently (this README, `CLAUDE.md`, `results/failures.md`) rather than silently swapped in; real, cited, peer-reviewed dataset, not synthetic | Absolute latency numbers here are not directly comparable to a run against `soc-Pokec` or similar - only the CognoDB-vs-others comparison *within this run* is meaningful |

## Known limitations

- **Network egress.** This repo was built inside a sandboxed remote
  session whose egress policy allows only GitHub and package registries.
  None of the five platforms, nor any non-GitHub dataset host, were
  reachable, and the Bolt protocol (raw TCP, non-443) is not proxyable
  there regardless of domain policy. See `results/failures.md` for the
  concrete attempts and denials, and `CLAUDE.md`'s "Known environment
  constraint" note.
- **No measurement has been made.** Every number that would normally be in
  this README is absent by design rather than invented - see Status above.
- **Advertised specs unknown for 4 of 5 platforms.** Only CognoDB's specs
  (quoted from the assignment PDF) are filled in; the rest need Stage 0.
- **`falkordb.py` and `arangodb.py` are unverified against live servers.**
  Both were checked against the *installed* Python client library's real
  method signatures (not guessed from memory), but neither has connected to
  an actual FalkorDB or ArangoDB instance. `bolt.py`'s `neo4j` driver usage
  is similarly unverified against a live server, though the Bolt/Cypher
  surface it uses is small and standard.
- **Track B (capped self-hosted, memory sweep) is scaffolded, not run.**
  `docker/compose.capped.yml` exists; `make capped` intentionally exits 1
  rather than claim a sweep that never happened.
- **`insert_edge` (the mixed workload's write query) is outside the
  equality gate.** The gate only compares read-only logical queries across
  platforms, since writes mutate state; there is currently no cross-platform
  check that a write "did the same thing" on every platform beyond each
  adapter using the same bind variables.
